# 照片、视频分类与私密展示实施方案

此文记录旧版单选 `slot` 方案；当前统一照片库的结构、兼容边界与上线步骤见 [统一照片库 V2](MEDIA-LIBRARY-V2.md)。

状态：本地代码已实现，尚未部署云函数或发布小程序。本阶段“私密”仅表示不对外展示；历史照片默认公开、待分类并保持原展示。

## 现状与约束

- `Photo.type` 已区分图片和视频；缺失时 `normalizeMediaData` 按图片处理。`slot` 是展示位置（`album`、`cover`、`story`、`qiuqiu`、`buding`），不能改作照片分类，否则首页、故事和猫咪区域会失效。
- `photo_content/draft` 保存主人草稿，`photo_content/published` 保存亲友展示。`getPhotos` 当前原样返回已发布数组；首页、照片册和故事页分别按 `slot` 取数据。照片册目前只有一个相册，照片和视频混排。
- 一张云文件可以被多个条目复用。`original`、`thumbnail`、`url`、视频 `coverUrl` 都可能引用同一个文件；删除检查已同时检查草稿和发布内容。
- 数据库客户端规则为 `read:false/write:false`，但现有文档要求云存储“所有用户可读”。小程序用 `wx.cloud.getTempFileURL` 将 File ID 换成临时链接。只隐藏卡片，不能使已经拿到 File ID 或链接的人失去文件访问能力。
- 现有限制为最多 60 条媒体安排，单图最多 30 MiB，单视频最多 60 秒/30 MB；新分类不改变这些限制、上传方式、路由和草稿/发布操作。

## 目标模型

顶层浏览为“照片”“视频”。照片分类固定为“婚纱照”“日常照”“927 宝鸡答谢宴”“928 临潼答谢宴”。分类是内容属性，独立于 `slot`；视频先只归入“视频”，不强行赋予照片分类。内部使用稳定代码（如 `wedding`、`daily`、`baoji_0927`、`lintong_0928`），中文名称只用于展示，避免以后改文案造成历史数据失配。

建议在现有媒体条目上增加可选 `category` 和 `visibility`（`public`/`private`），不改现有字段名、集合名或路由。读取边界将缺失的 `visibility` 解释为 `public`，保持历史展示；缺失的图片 `category` 解释为“待分类”，仅在主人端提示，不自动猜测活动。旧视频没有分类字段。占位条目和本地配置仍按当前逻辑处理。

“待分类”是兼容状态，不是第五个对外分类：旧相册内容在完成整理前继续出现在“全部照片”，主人可逐条归入四类。新上传照片在草稿中选择分类；服务端需按已有条目 ID 判断新增图片，拒绝新增但未分类的发布，不阻断旧内容继续展示。主人可把内容设为私密；更新展示后，私密内容保留在草稿供管理，不出现在亲友的任何列表、封面、故事、猫咪区域、视频封面、预热或大图预览中。仅保存草稿时，亲友仍看到上次发布的内容，界面必须明确提示。

## 私密边界与后续升级

**本阶段**：`publishPhotos` 或 `getPhotos` 在服务端统一过滤私密条目，所有访客页面只使用过滤后的结果；主人草稿保留全部。旧公开链接与当前云存储可读规则仍可能让持有链接的人读取文件，因此界面必须明确这不是文件级保密。现阶段不修改云存储规则、不迁移文件、不声称撤销既有链接。

**预留升级边界**：把“条目是否可对外返回”的判断集中在服务端，把“根据 File ID 获取展示地址”的调用集中在现有 `services/cloud-file-url.ts`，不要在新页面直接调用 `wx.cloud.getTempFileURL`。将来需要文件级私密时，可在这一边界加入经服务端鉴权的地址签发，并核验 CloudBase 是否支持按路径区分存储读取权限；届时再设计旧文件迁移。不要现在新增空接口或未经使用的云函数，也不能直接把整个存储改成禁止读取，否则现有公开照片、视频、静态图片或音乐可能失效。已公开链接仍可能在有效期内可用，未来升级也不能承诺瞬时撤回。

无论选哪一级，复用同一个 File ID 的所有条目必须遵循一致的可见性：不允许一个条目标私密、另一个仍公开相同原图或封面。发布前由服务端检查 `original`、`thumbnail`、`url`、`coverUrl` 的交叉引用，并要求主人统一可见性或另存独立文件。清理文件前继续检查草稿和发布两侧引用。

## 实施与部署顺序

1. **先建立基线与备份**：导出当前 `draft`/`published` 文档及存储规则，仅作为可恢复快照；记录已发布条目、历史字符串/`imageUrl`、复用文件和静态配置。确认现有手机上传、播放、原图预览均正常。
2. **服务端先兼容新字段**：`cloudfunctions/weddingApi/photos.js` 已增加分类、可见性白名单校验与保存，保留旧字段和旧 action；访客 `getPhotos` 仅返回公开条目。服务端发布时私密内容只留主人草稿。部署时必须先更新云函数，再上传新版小程序；用旧开发版验证遗漏新字段的提交不会清除已有分类或私密状态。
3. **读取边界兼容**：`models.ts`、`services/media.ts`、`services/photos.ts` 已增加可选字段及旧数据默认解释；分类和可见性变化已纳入 `photoArrangementSignature`。不改写历史数据库以补默认值。
4. **主人端管理**：`pages/photos` 保留上传队列、用途、排序、复用、草稿和更新展示；已增加类型筛选、图片分类选择及私密开关。新选择和 File ID 导入的图片先存为“待分类”，视频不显示照片分类；待分类新增图片不能更新展示。同文件私密开关同步所有复用条目，云端仍会拒绝冲突提交。
5. **访客展示**：现有 `pages/gallery` 已加入“照片 / 视频”总览及四类照片筛选，没有更换页面 path。首页、故事和猫咪依旧按 `slot` 展示；访客服务层再次过滤私密条目。首次读取暂不可用时不展示可能已设私密的静态云图片；缺少发布记录时仍保留现有本地配置回退。原图/WebP 回退、视频播放和预热路径保持原样。
6. **后续文件级私密（本阶段不实施）**：若以后需要，单独完成存储规则、受限文件上传/读取、已公开文件迁移和旧链接有效期验收。此步骤需要真实云环境及管理员/访客双账号验证，不能仅靠本地 mock 证明。

## 关键回归

- 旧数据：无 `type`、字符串 URL、`imageUrl`、现有 `slot`、空发布数组均按原行为读取；未分类旧照片不消失。原图上传、WebP/PNG/原图回退和视频封面/播放不受影响。
- 草稿/发布：保存草稿不改变访客页；更新展示后四类数量、顺序、照片与视频分离正确；重新进入、断网、失败重试、两名管理员先后编辑保持可预期。
- 私密：访客直调 `getPhotos` 看不到私密条目及任何私密 File ID；首页、故事、猫咪、相册、大图预览、视频封面、预热与分享均不泄露。主人可管理和重新公开；同一文件复用为一公一私时被阻止。
- 本阶段需确认私密条目不在公开 API 和界面出现，同时明确记录：持有旧 File ID 或旧临时链接仍可能访问文件。未来做文件级私密时再检查旧链接有效期及迁移结果，并验证公开媒体、音乐和本地配置图片仍正常。
- 校验 WXML 事件绑定、`setData`、云函数 action/参数、60 条上限、删除引用检查、真实 iPhone/Android 与开发者工具域名配置。

## 已确认的产品决定

1. 本阶段私密仅隐藏对外展示；保留将来实现文件级访问控制的代码边界，但此时不新增无用途接口。
2. 历史已发布内容默认公开且“待分类”，保持原展示，待主人逐条分类。不自动把所有旧照片判定为婚纱照，也不让旧内容消失。

本地已执行类型检查、ESLint、59 项自动测试、16 个 WXML 与 17 个 WXSS 原生编译，以及浏览器 UI 回归。没有执行线上数据库备份、云函数部署、存储规则变更或真机双账号验收；上线前按本节顺序完成。
